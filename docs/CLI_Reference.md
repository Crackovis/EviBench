# EviBench CLI Reference

Complete reference for every command available under the `imputebench` CLI (ImputeBench module
of the EviBench platform).

Operational safety details for typed configuration, admin backup/status, managed
lab sessions, and safe update previews are documented in
[Operational_CLI_Foundations.md](Operational_CLI_Foundations.md).

---

## Overview

```
imputebench
├── dataset         Manage dataset registrations
├── algorithm        Manage algorithm registrations
├── plugin           Manage algorithm plugins
├── ingest           Inspect and ingest external resources
├── masking          Manage masking scenarios
├── run              Manage experiment runs
├── recipe           Manage recipe books
├── result           Manage experiment results
├── locality         Inspect and normalize path locality
├── calibration      Manage spatial calibrations
├── viewer           Manage spatial viewers
├── compare          Manage result comparisons
├── lab              Interactive lab controls
├── env              Runtime environment diagnostics
├── config           Manage ImputeBench configuration
├── maintenance      Junk cleanup and data management     ← v1.2+
├── audit            Audit and diagnostic tools          ← unified (ex-scripts/)
├── validate         Validation acceptance gates         ← unified (ex-scripts/)
├── repair           Repair and maintenance tools        ← unified (ex-scripts/)
├── admin            Administrative tools                ← unified (ex-scripts/)
├── st               Spatio-temporal experiment lane (graph/mask/plan/run/evidence/gates)
├── temporal         Temporal experiment lane (recipe/prepare/experiment/evidence/gates)
├── study            Dataset studies (profile, stationarity, diagnostics)
├── evidence gate    Evaluate evidence completeness (thesis guardrail)
├── thesis dataset   Dataset characterization for thesis
├── thesis missingness  Missingness characterization for thesis
├── thesis compare   Comparison reports for thesis
├── thesis training  Training evidence for thesis
├── thesis algorithms  Algorithm inventory for thesis
├── thesis all       Run all thesis evidence packs
└── thesis gates     Evidence readiness matrix & quality report
```

---

## Quick Start

The three most important commands for the CLI-first workflow:

```bash
# 1. Discover available recipe books (safe, non-launching)
python -m imputebench experiment temporal recipe list

# 2. Run a smoke classical experiment
python -m imputebench experiment temporal experiment run \
  --recipe-book official_londonaq_classical_benchmark \
  --tier smoke --algorithms mean --mask-families mcar --rates 0.3 \
  --realizations 1 --execution-class classical

# 3. Characterize a dataset
python -m imputebench study dataset profile --dataset-id london_aq
```

## Progress Reporting Options

Long-running study, temporal, spatio-temporal, and thesis commands can report
interactive progress and machine-readable JSONL events. The framework is
documented in [Progress_Reporting_Framework.md](Progress_Reporting_Framework.md).

Root-level options appear before the command group and command-local options
appear on the long-running command itself. Local options override root-level
defaults.

| Option | Values | Description |
|---|---|---|
| `--progress` / `--no-progress` | flag | Force terminal progress on/off |
| `--progress-backend` | `auto`, `tqdm`, `rich`, `silent` | Select terminal progress backend |
| `--progress-event-log <path>` | path | Write JSONL progress events without corrupting stdout |

Examples:

```bash
python -m imputebench --progress-backend rich study temporal arma-order --dataset-id london_aq
python -m imputebench experiment temporal prepare materialize --recipe-book official_londonaq_classical_benchmark --progress-event-log logs/temporal_prepare.jsonl
python -m imputebench experiment st experiment run --tier smoke --dataset-id london_aq --progress-backend silent --progress-event-log logs/st.jsonl
python -m imputebench thesis all --no-progress
```

Progress output is additive: JSON command output remains on stdout, terminal
progress uses stderr/backends, and event logs are written only when requested.

> **Legacy path:** `imputebench dataset` — still works as a hidden alias.

| Command | Description |
|---|---|
| `list` | List all registered datasets |
| `register --name ... --path ...` | Register a new dataset |
| `update <id> [--name ...] [--path ...] [--description ...] [--format ...] [--pollutants ...]` | Patch supplied dataset fields only |
| `show <id>` | Show dataset details as JSON |
| `delete <id>` | Delete a dataset |

```bash
imputebench data dataset list
imputebench data dataset register --name "LondonAQ" --path "./data/london" --format dat-tsv --pollutants "NO,NO2,O3,SO2"
imputebench data dataset update ds_a1b2c3 --description "Official LondonAQ benchmark dataset"
imputebench data dataset show ds_a1b2c3
imputebench data dataset delete ds_a1b2c3
```

`dataset update` refuses empty updates and preserves every unspecified field.
Paths are normalized through the path-locality service before persistence.

### `imputebench methods algorithm`

> **Legacy path:** `imputebench algorithm` — still works as a hidden alias.

| Command | Description |
|---|---|
| `list` | List registered algorithms |
| `list-builtin` | List built-in algorithms with status/requirements |
| `register --name ... --family ... --entry ...` | Register a new algorithm |
| `update <id> [--name ...] [--family ...] [--description ...] [--default-config JSON] [--dependencies ...] [--dry-run] [--format table\|json]` | Patch supplied algorithm fields only, with optional preview/diff output |
| `show <id>` | Show algorithm details as JSON |
| `delete <id>` | Delete an algorithm |

```bash
imputebench methods algorithm list
imputebench methods algorithm list-builtin
imputebench methods algorithm register --name "BRITS" --family dl_temporal --entry "imputebench.algorithms.dl_temporal.brits:BRITSImputer"
imputebench methods algorithm update alg_x1y2z3 --default-config '{"epochs": 100}' --dependencies "torch,numpy"
imputebench methods algorithm update alg_x1y2z3 --description "Validated profile" --dry-run --format table
imputebench methods algorithm update alg_x1y2z3 --default-config '{"epochs": 100}' --dry-run --format json
imputebench methods algorithm show alg_x1y2z3
```

`algorithm update` validates the family choice, requires `--default-config` to be
valid JSON, and leaves the entry point and all omitted fields unchanged. Use
`--dry-run` to emit an `EntityPatchReport` preview without persistence, and use
`--format json` when automation needs the before/after field diff.

### `imputebench data masking`

> **Legacy path:** `imputebench masking` — still works as a hidden alias.

| Command | Description |
|---|---|
| `list` | List registered masking scenarios |
| `create --name ... --type ... --rate ...` | Create a new masking scenario |
| `update <id> [--name ...] [--rate ...] [--params JSON] [--dry-run] [--format table\|json]` | Patch supplied masking fields only, with optional preview/diff output |
| `show <id>` | Show scenario details as JSON |
| `delete <id>` | Delete a masking scenario |

```bash
imputebench data masking list
imputebench data masking create --name "MCAR 10%" --type mcar --rate 0.1
imputebench data masking create --name "Temporal Block 20%" --type temporal_block --rate 0.2 --params '{"block_size": 10}'
```

`masking update` validates that supplied rates remain within `[0, 1]`, requires
`--params` to be valid JSON, and preserves the masking type. Structured preview
mode requires `--params` to be a JSON object and reports changes through the same
`EntityPatchReport` model as algorithm updates.

## Experiment Execution

### `imputebench experiment run`

> **Legacy path:** `imputebench run` — still works as a hidden alias.

| Command | Description |
|---|---|
| `create --dataset ... --algorithms ... --masking ...` | Create a run plan |
| `list [--dataset-id ...] [--algorithm-id ...] [--status ...] [--limit N] [--format table\|json]` | List run plans with optional filters |
| `show <run_id> [--format table\|json] [--include-results\|--no-include-results]` | Show run metadata, lifecycle, artifacts, timing, and optional result summaries |
| `delete <run_id> [--cascade] [--force] [--dry-run] [--format table\|json]` | Delete a run safely after impact preview |
| `execute <run_id>` | Execute a run and display results |
| `status <run_id>` | Check run execution status |

```bash
imputebench experiment run create --dataset ds_a1b2c3 --algorithms alg1,alg2 --masking mask1,mask2 --metrics mae,rmse
imputebench experiment run list --dataset-id ds_a1b2c3 --status completed --format table
imputebench experiment run show run_d4e5f6 --no-include-results
imputebench experiment run delete run_d4e5f6 --dry-run
imputebench experiment run delete run_d4e5f6 --cascade --force
imputebench experiment run execute run_d4e5f6
imputebench experiment run status run_d4e5f6
```

`run delete` is destructive and defaults to the safe path: record-only deletion is
attempted only when the impact model reports no linked results, artifact paths,
timing spans, or catalog rows. Use `--cascade` to intentionally invoke the full
run-service cascade, and use `--dry-run` to preview the impact without mutation.

### `imputebench experiment recipe`

> New in v0.3.0. Recipe books define experiment grids in declarative YAML, backed
> by the SQLite recipe registry. Built-in books provide official benchmarks.
> Clone to customize. See [Recipe_Book_Architecture.md](Recipe_Book_Architecture.md)
> for architecture details.

| Command | Description |
|---|---|
| `list [--tier <tier>]` | List available recipe books |
| `show <book_id>` | Show recipe book details as JSON |
| `create --name ... --yaml-path ...` | Create a new recipe book from YAML |
| `clone <book_id> --name ...` | Clone an existing recipe book |
| `update <book_id> [--name ...] [--description ...]` | Update recipe book metadata |
| `delete <book_id> [--force]` | Delete a recipe book |
| `validate <book_id>` | Validate recipe book YAML integrity |
| `export <book_id> --output ...` | Export recipe book as YAML |
| `history <book_id>` | Show recipe book revision history |
| `materialize <book_id> --dataset-id ...` | Materialize plans from recipe book |
| `entry list <book_id>` | List entries in a recipe book |
| `entry show <book_id> <entry_id>` | Show entry details |
| `entry add <book_id> --recipe ...` | Add an entry to a recipe book |
| `entry update <book_id> <entry_id> [--field ...]` | Update a recipe book entry |
| `entry remove <book_id> <entry_id>` | Remove an entry from a recipe book |
| `algorithm add <book_id> --algorithm-id ...` | Add an algorithm to a recipe book |
| `algorithm remove <book_id> --algorithm-id ...` | Remove an algorithm from a recipe book |

```bash
# List all recipe books
imputebench experiment recipe list

# List Tier A recipes only
imputebench experiment recipe list --tier a

# Show a recipe book
imputebench experiment recipe show official_londonaq_classical_benchmark

# Clone a built-in book to customize
imputebench experiment recipe clone official_londonaq_classical_benchmark --name my_custom_benchmark

# Validate a recipe book
imputebench experiment recipe validate my_custom_benchmark

# Add an algorithm to a recipe book
imputebench experiment recipe algorithm add my_custom_benchmark --algorithm-id alg_brits

# Inspect entries
imputebench experiment recipe entry list my_custom_benchmark

# Materialize experiment plans from a recipe book
imputebench experiment recipe materialize official_londonaq_classical_benchmark --dataset-id london_aq
```

All recipe book operations are non-destructive by default. `validate` checks YAML
schema integrity. `materialize` produces experiment plans without executing them.
`delete` prompts for confirmation unless `--force` is passed.

### `imputebench admin config`

> **Legacy path:** `imputebench config` — still works as a hidden alias.

| Command | Description |
|---|---|
| `show [--format table\|json] [--keys <csv>] [--sources\|--no-sources]` | Display effective mutable preferences and read-only runtime facts |
| `set <key> <value> [--dry-run] [--format table\|json]` | Persist a whitelisted mutable preference with validation and atomic write |
| `validate [--file <path>] [--format table\|json]` | Validate project configuration YAML |
| `style show [--file <path>]` | Display style configuration as JSON |
| `style validate <file>` | Validate a style configuration file |

```bash
imputebench admin config show --sources

imputebench admin config show --keys cli_default_output_format,lab_default_port
imputebench admin config set lab_default_port 8600 --dry-run --format table

imputebench admin config validate --file config/imputebench.yaml
imputebench admin config style show
imputebench admin config style validate config/style.yaml
```

`config set` is intentionally limited to mutable preference keys such as
`cli_default_output_format`, `cli_progress_mode`, `cli_progress_backend`,
`lab_default_port`, `lab_default_conda_env`, and
`admin_backup_compression`. It cannot change runtime directory paths such as
`root_dir`, `data_dir`, `registry_dir`, `results_dir`, `plugins_dir`,
`figures_dir`, or `metadata_db_path`; those are read-only facts resolved by the
runtime path layer. Project YAML writes are atomic and preserve the previous file
as `.bak`.

### `imputebench lab`

| Command | Description |
|---|---|
| `start [--port <N>] [--detach] [--stdout-log <path>] [--stderr-log <path>]` | Launch the Streamlit interactive workbench; detached mode registers a managed session UUID |
| `start --force` | Kill existing process on port and restart |
| `list [--active-only] [--include-stale\|--no-include-stale] [--reconcile\|--no-reconcile] [--format table\|json]` | List managed lab sessions from the registry |
| `show <session_id> [--format table\|json]` | Show one managed lab session by UUID |
| `stop <session_id> [--dry-run] [--timeout-seconds N] [--force] [--format table\|json]` | Stop a verified ImputeBench-owned lab process |
| `cleanup [--stale-only\|--all-stopped] [--dry-run] [--force] [--format table\|json]` | Remove stale/stopped session registry entries |

```bash
imputebench lab start
imputebench lab start --port 8600
imputebench lab start --detach --stdout-log data/runtime/lab_logs/lab.out.log --stderr-log data/runtime/lab_logs/lab.err.log
imputebench lab list --active-only
imputebench lab list --format json
imputebench lab show <SESSION_ID> --format table
imputebench lab stop <SESSION_ID> --dry-run --format json
imputebench lab stop <SESSION_ID> --timeout-seconds 15
imputebench lab cleanup --dry-run
imputebench lab cleanup --all-stopped --force
imputebench lab --force start
```

Managed lab sessions are identified by UUID, not by PID. `lab stop` requires
verified process ownership (PID, creation time when available, executable, and
command fingerprint) before termination. `--force` may escalate the termination
method after ownership is verified, but it never bypasses identity verification
and cannot be used to terminate arbitrary PIDs.

`plugin delete` never directly purges plugin files. It performs canonical-root
containment checks, refuses built-in plugin roots, previews impact by default,
and moves removable plugin bundles into quarantine. With cascade enabled, the

## Spatio-Temporal Lane

### `imputebench experiment st`

> **Legacy path:** `imputebench experiment st` — still works as a hidden alias.

The `st` command group is the **orchestration authority** for the spatio-temporal
LondonAQ experiment lane: it builds graph assets, mask banks, plans, runs,
evidence packs, gate reports, and the official campaign certification. GUI or
dashboard layers only read the artifacts the CLI produces — the CLI is the
source of truth for ST experiment construction.

📖 **Full documentation:** [ST_Experiment_CLI_Philosophy.md](ST_Experiment_CLI_Philosophy.md)
— CLI-first philosophy, core concepts, full lifecycle, design invariants,
complete command reference, certification semantics, and the replication
blueprint for future lanes.

```
imputebench experiment st
├── env                    Python/PyTorch/CUDA diagnostic + forward-pass smoke test

├── tensor                 Inspect the [T,N,F] graph tensor adapter
├── mask-bank              Create graph-aware benchmark mask banks
├── recipe                 Recipe book: list/inspect/validate/plan/materialize (dry-run only)
├── plan                   Generate official plans bound to a graph + mask banks
├── preflight              Validate environment before plan creation/execution
├── experiment             run (full pipeline) / reset / certify-official
├── run                    Execute one ST run with ST-specific preflight
├── compare                Materialize graph-aware comparison tables
├── evidence               Chapter 06 evidence: export/mirror/audit/visual-audit
├── gate                   Evaluate one of 17 readiness gate profiles
├── scientific             SCI-FIX09 final scientific readiness gate
├── readiness              ST_OFFICIAL_READINESS_REPORT generation
├── training               Training tiers, adequacy, convergence (SCI-FIX02/03)
├── audit                  Post-campaign database audit
├── figures                Extended Chapter 06 figure gallery
├── chapter06-readme       Refresh the chapter06 evidence README
└── regenerate-chapter06   One-shot 11-step evidence pack regeneration
```

Most common launch command (full pipeline: graph → mask → plan → execute → evidence;
this starts long-running training):

```bash
python -m imputebench experiment st experiment run \
  --tier a --dataset-id london_aq \
  --graph-policy correlation_train_v1 \
  --realizations 5 --epochs 100 \
  --early-stopping --checkpoint-policy best_validation_loss \
  --skip-completed \
  --event-log data/logs/st_events.jsonl \
  --progress-file data/logs/st_progress.json

# Universal progress reporting (terminal/backend + JSONL event log)
python -m imputebench experiment st experiment run \
  --tier smoke --dataset-id london_aq \
  --graph-policy grid_4n_v1 --mask-family mcar --algorithm stgcn \
  --realizations 1 --progress-backend silent \
  --progress-event-log data/logs/st_progress_events.jsonl
```

`st experiment run` progress covers dataset tensor loading, graph assets, mask
banks, plan generation, run execution, evidence export, gates, and certification
/ README steps. The progress adapter preserves run IDs, graph IDs, mask-bank IDs,
rates, realization counts, and JSON stdout integrity.

Common inspection / regeneration commands (safe, non-launching):

```bash
imputebench experiment st env                                   # GPU readiness
imputebench experiment st recipe list --tier tier_a             # official recipes
imputebench experiment st graph list                            # persisted graph assets
imputebench experiment st gate --profile scientific_ready       # SCI-FIX09 verdict
imputebench experiment st scientific gate report                # final scientific gate
imputebench experiment st experiment certify-official --dry-run # campaign certification checks
imputebench experiment st chapter06-readme                      # refresh evidence README
```

Key semantics (detailed in the philosophy doc):

- **Containers vs. cells** — the official Tier-A campaign is 24 ExperimentRun
  containers (4 algorithms × 6 mask families) carrying 120 evaluation cells
  (× 5 mask realizations).
- **Calibration vs. official readiness** — `calibration_scientific_ready` and
  `official_tier_a_campaign_complete` are distinct gate fields; passing the
  calibration gate never implies the official campaign ran.
- **Bounded claims only** — gates allow controlled-comparison claims under the
  stated conditions; superiority/state-of-the-art/paper-reproduction claims are
  permanently blocked by the claim policy.

## Thesis evidence export (Sheet 15)

### `imputebench thesis export-human`

Assembles a human-readable, offline, portable evidence pack on top of the
existing technical export engine. Selection is SQL-first (same query engine as
`results evidence export-batch`); no directory scan selects results.

```bash
imputebench thesis export-human \
  --recipe-book official_londonaq_classical_benchmark --tier a \
  --algorithm-id linear_interpolation --algorithm-id dacpi \
  --output-dir ./evidence_pack

# With paired statistics (optional extra)
pip install -e ".[evidence-stats]"
imputebench thesis export-human --comparison-id <id> --include-stats \
  --output-dir ./evidence_pack
```

The pack contains `README.md`, a single offline `evidence_dashboard.html`,
`tables/`, `figures/`, `stats/`, and `provenance/` (manifest, source manifest,
id map, selection, blocked items, checksums). Visible names are human (never a
UUID); BEST highlighting and significance claims are gated by cohort
comparability; the grade is bounded by the most restrictive source.

[CLI options](Human_Readable_Evidence_Export_CLI.md) ·
