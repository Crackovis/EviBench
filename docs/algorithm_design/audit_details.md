# Unified Audit — Technical Reference

Complete technical documentation for the EviBench unified algorithm audit.
Covers the 5-stage pipeline, database schema, resolution rules, and
customisation.

---

## Architecture

The unified audit (`imputebench audit run`) replaces five separate legacy audits
(AD0 design inventory, AD1 cards, AD1.5 conformance, AD2 execution truth,
AD3 comparison validity) with a single coherent pipeline.

```
Stage 1 ── Inventory       ── Plugin registry scan, duplicate filtering
Stage 2 ── Card Specs      ── Scientific card generation (17 algorithms)
Stage 3 ── Conformance     ── Static/behavior probes vs declared principles
Stage 4 ── Execution Truth ── SQLite queries → AUTHORITATIVE verdict
Stage 5 ── Comparison      ── Benchmark parity, mask bank, realization coverage
             │
             ▼
      Resolution (AD2 > AD1.5 > AD0)
             │
             ▼
      Unified Audit Report
```

All five stages are executed in order. Stage 4 (execution truth) is
**authoritative** — its verdicts override any contradictory findings from
earlier stages.

---

## Stage 1 — Inventory

**Source**: Plugin registry (`plugins/*/imputebench_plugin.json`)

Each plugin directory is scanned for its manifest. The manifest declares the
algorithm's name, family, role, and implementation kind. Additional checks:

- **Contract verification**: Does the plugin directory contain a README?
  (serves as a proxy for fit/impute/get_info availability)
- **Test detection**: Does `tests/plugins/{algorithm}/` exist with files?
- **Source file discovery**: Lists all `.py` files in the plugin directory

**Duplicate filtering**: BRITS and Mean can appear twice in the registry
(legacy duplicate entries). The inventory stage groups by (name, family) and
selects the best candidate using scoring rules:
1. Prefer `plugin` implementation over `builtin`
2. Prefer valid callable contract
3. Prefer entries with tests
4. Prefer non-temp paths
5. Prefer fewer audit errors/warnings

The canonical census is exactly **17 algorithms**.

**Database query** (optional bridge): When `metadata.db` is available, the
inventory can enrich results with runtime evidence from the `results` and
`runs` tables.

---

## Stage 2 — Card Specs

Generates one scientific card per canonical algorithm. Each card contains
12 sections: position in ImputeBench, one-paragraph summary, scientific
principle, mathematical definition, fit behavior, impute behavior,
configuration surface, implementation mapping, execution evidence,
comparison readiness, limitations, and references.

The card's evidence status reflects the **resolved** verdict, not the raw
AD0 status. If AD2 confirms `execution_ready`, the card shows that.

---

## Stage 3 — Conformance

**Source**: Static and behavior probes

Two probe types verify that an algorithm's implementation matches its
declared scientific principle:

- **Static probe**: Source-code pattern matching. Checks for expected
  function calls, imports, and structural patterns (e.g., `pandas.interpolate`
  for NearestInterpolation, `torch.nn.GRU` for GRU-D).
- **Behavior probe**: Deterministic synthetic tests. Runs the algorithm
  on small controlled inputs and verifies numerical outputs.

**AD2 bridge**: For deep learning algorithms, static probes alone are
insufficient to verify correctness. When AD2 execution truth confirms
`execution_ready`, the conformance verdict is upgraded from
`partial_conformance` to `mostly_conformant`, with a note that runtime
execution bridges the gap.

**Verdicts**: `conformant`, `mostly_conformant`, `partial_conformance`,
`non_conformant`, `not_auditable`, `not_applicable`.

---

## Stage 4 — Execution Truth (AUTHORITATIVE)

**Source**: SQLite database (`data/metadata.db`)

This is the most important stage. It queries the `results` table (JOINed with
`algorithms`) and `runtime_timing_spans` to extract runtime evidence.

### Family-specific gates

**Deep Learning (RNN, LSTM, GRU, GRU-D, BRITS, SAITS, SAITS-LC, SAITS-LCH)**:
- Results exist for train, validate, and test phases
- `actual_execution_class` is `scientific_dl`
- `mock_mode_used` is `false`
- A checkpoint was selected (`selected_checkpoint_path` is non-empty)
- Training history path exists
- Prediction fingerprint exists (`evaluation_support_fingerprint` is non-empty)
- Runtime timing spans exist

**Baselines (Mean, Median, LinearInterpolation, LOCF)**:
- Results exist with metrics and timing
- Mask evidence is traceable
- No checkpoint/DL requirements

**Classical (BackwardFill, MovingAverage, NearestInterpolation, SeasonalNaive, ExponentialSmoothing)**:
- Results exist with metrics and timing
- Mask evidence is traceable

### Table references

| Table | Role |
|---|---|
| `results` | Per-algorithm execution results with phase, checkpoint, artifact paths |
| `algorithms` | Maps algorithm UUIDs to names and families |
| `runtime_timing_spans` | Per-phase timing evidence with duration and device info |

---

## Stage 5 — Comparison Validity

**Source**: SQLite database

Checks whether algorithms can be compared fairly in a benchmark:

- **Benchmark contract parity**: All units share the same contract ID
- **Mask bank parity**: All units share the same mask bank ID
- **Evaluation support**: All units share the same fingerprint
- **Realization coverage**: All units cover the same set of realizations

The `comparison_specs` table is queried for non-archived specs. Unit IDs
are extracted from `unit_ids_json`.

**Statuses**: `thesis_grade_ready`, `exploratory_only`, `invalid`, `needs_refresh`, `not_evaluated`.

---

## Resolution Hierarchy

When stages produce contradictory results, the hierarchy resolves:

```
AD2 (execution truth) > AD1.5 (conformance) > AD0 (inventory)
```

### Rules

| AD2 says | AD1.5 says | AD0 says | → Resolved |
|---|---|---|---|
| `execution_ready` | `partial_conformance` | `partial` | `execution_ready` |
| `execution_partial` | `mostly_conformant` | `partial` | `execution_partial` |
| `execution_invalid` | anything | anything | `execution_invalid` |
| `not_runnable` | anything | anything | `not_runnable` |
| `not_executed` | anything | `partial` | `partial` (AD0 fallback) |

**AD3 is independent** — it checks cross-algorithm compatibility, not individual
status. A comparison being `exploratory_only` does not affect an algorithm's
execution truth status.

## Database schema (key tables)

### `algorithms`
```
id TEXT PRIMARY KEY    — UUID
name TEXT              — e.g., "Simple RNN"
family TEXT            — e.g., "dl_temporal"
plugin_path TEXT       — e.g., "plugins/rnn"
payload_json TEXT      — Full algorithm metadata
```

### `results`
```
id TEXT PRIMARY KEY
algorithm_id TEXT      — FK → algorithms.id
phase_key TEXT         — "train", "validate", "test"
selected_checkpoint_path TEXT
training_history_path TEXT
evaluation_support_fingerprint TEXT
benchmark_contract_id TEXT
benchmark_mask_bank_id TEXT
metrics_json TEXT
created_at TEXT
completed_at TEXT
```

### `runtime_timing_spans`
```
algorithm_id TEXT      — FK → algorithms.id
phase_key TEXT         — "train", "validate", "test"
duration_ms INTEGER
execution_class TEXT   — "scientific_dl", "mock", etc.
```

### `comparison_specs`
```
id TEXT PRIMARY KEY
comparison_profile TEXT
archived INTEGER       — 0 = active, 1 = archived
unit_ids_json TEXT     — JSON array of algorithm IDs
```

## CLI reference

```bash
# Full audit
imputebench audit run

# Skip specific stages (comma-separated)
imputebench audit run --skip-stages conformance,comparison

# Custom directories
imputebench audit run \
  --output-dir data/audits/unified \
  --docs-dir docs/algorithm_design

imputebench audit run --verbose
```

runtime-timing, benchmark-staleness, raw-labels, retire, size) remain available
for specialised diagnostics.

|---|---|
