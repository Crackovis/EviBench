# Experiment Runs — Shared Benchmark Contract Workflow

This document explains what changes in **Experiment Runs** when a plan is created **with a shared benchmark contract**.

It applies to both:

- classical plans,
- deep-learning plans.

The purpose of this workflow is not just to run a plan.
It is to bind that plan to a shared benchmark identity so that downstream results remain aligned, traceable, and comparison-ready.

## What this workflow adds

A normal plan already describes what should run.
A benchmark-aware plan adds a second layer:

- which shared benchmark contract the plan belongs to,
- which mask bank that contract references,
- which realization IDs define the benchmark cohort,
- which eligibility fingerprint defines the evaluation support,
- whether execution should be blocked if that benchmark identity is missing or incoherent.

That is why this document should be read as a contract-aware overlay on top of the standard workflow.

## What this document does not replace

This document does not replace the base workflow documents.

Use it together with:

- `Experiment_Runs_Classical_Workflow.md`
- `Experiment_Runs_DL_Workflow.md`

Those documents explain how classical and DL plans operate on their own.
This one explains what changes once a shared benchmark contract is attached.

## When to use a shared benchmark contract

Use a shared benchmark contract when several plans are expected to remain comparable under the same benchmark identity.

In practice, that means you want more than local execution convenience.
You want a stable comparison frame that can be carried through:

- plan creation,
- execution,
- result persistence,
- and later comparison work.

If that is not needed, the simpler non-contract workflow is enough.

## Where benchmark contracts come from

`Experiment_Runs` does not invent benchmark contracts on its own.
It expects them to exist already.

If no contract exists for the selected dataset, the page explicitly points you to:

- **Comparison Studio**
- **Benchmark Assets Manager**

That is the upstream place where shared benchmark assets are defined and maintained.

## The benchmark-aware route at a glance

```mermaid
flowchart LR
    A[Create or select benchmark assets] --> B[Attach contract in Create Plan]
    B --> C[Save benchmark-aware plan]
    C --> D[Read preflight and benchmark truth]
    D --> E[Execute under contract]
    E --> F[Persist benchmark identity into results]
    F --> G[Use in Comparison Studio]
```

This is the main idea:
a benchmark contract is not only a UI selection.
It becomes part of the run and then part of the results.

## Step 1 — Attach the contract in Create Plan

Go to **Create Plan** as usual.

Once a dataset is selected, the page reveals a dedicated section named:

- **Shared Benchmark Contract**

This section is where the benchmark-aware workflow begins.

### Turn on shared benchmark mode

Use the checkbox:

- **Use shared benchmark contract**

If this remains off, the plan stays in the ordinary non-contract workflow.
If it is turned on, the plan starts expecting benchmark identity data.

### Optional strict mode

The same section also exposes:

- **Strict**

This matters a lot.
It is not just an informational flag.
It tells the workflow whether missing or incoherent benchmark attachment should remain a warning or become a blocking condition.

### Select the contract

The contract list is filtered by dataset.
That keeps the selection tied to the current plan context.

Once a contract is selected, the page exposes key details directly:

- dataset,
- mask bank,
- number of realizations,
- eligibility fingerprint,
- phase scope,
- selection scope.

At this stage, the operator should not read the contract as a label only.
It is the benchmark identity that will be copied into the plan.

## Step 2 — Understand what gets stored in the plan

When a benchmark-aware plan is saved, the run model carries explicit benchmark fields.
That includes:

- `benchmark_contract_id`
- `benchmark_mask_bank_id`
- `benchmark_realization_ids`
- `evaluation_support_fingerprint`
- `shared_benchmark_required`
- `benchmark_phase_scope`
- `benchmark_selection_phase_scope`

This is important because the benchmark context is not reconstructed later by guesswork.
It is stored with the run itself.

In other words, the plan becomes benchmark-aware as a persisted object, not just as a temporary UI state.

## Step 3 — Read the benchmark surfaces in Select & Execute

Once a benchmark-aware plan is selected in **Select & Execute**, the page exposes several operator blocks.
Three of them matter most in this workflow:

- **Execution class & runtime truth**
- **Preflight summary**
- **Benchmark truth**

## Execution class & runtime truth

This block still shows the normal operational truth:

- requested execution class,
- actual execution class,
- compute engine.

But when a benchmark-aware plan is attached, the same block also carries a compact benchmark status badge.
That helps you see, at a glance, whether the current plan is operating:

- without benchmark,
- with an attached shared contract,
- or in a degraded benchmark state.

This is useful because the operator does not need to leave the execution surface to understand whether the run is benchmark-aware.

## Preflight summary

In the benchmark-aware workflow, preflight becomes much more important.

The page can check whether the attached benchmark contract remains coherent with the selected run.
That includes checks such as:

- dataset match,
- presence of a mask bank,
- presence of realization IDs,
- eligibility fingerprint coherence,
- semantic mismatch between strict shared benchmark and mock/smoke-style execution paths.

### What strict mode changes

Strict mode is the main turning point.

Without strict mode, incoherence can remain a warning.
With strict mode, some missing or invalid conditions become execution blockers.

A simple way to think about it:

- **non-strict**: benchmark attachment is advisory but visible,
- **strict**: benchmark attachment becomes an execution contract.

That is the right mental model for the operator.

## Benchmark truth

This block is the most explicit benchmark surface in the execution UI.

It displays benchmark-specific fields such as:

- contract ID,
- mask bank ID,
- realization count,
- eligibility fingerprint,
- and a benchmark status.

The status is especially important.
The page can surface states such as:

- **none**
- **attached**
- **degraded**

### How to read the status

#### none

No shared benchmark contract is attached.
That means the run is outside the contract-aware workflow.

#### attached

The shared benchmark identity is present and the plan has benchmark realization information attached.
This is the expected healthy state for a benchmark-aware plan.

#### degraded

A contract is present, but the benchmark identity is incomplete or weakened.
Typical causes include missing realization identity or related attachment gaps.

This state matters because it means the plan is no longer as strong, stable, or portable for downstream comparison as it should be.

## Step 4 — Execute under the contract

Once the plan is benchmark-aware and passes the necessary checks, execution proceeds according to its normal base class:

- classical plans still execute in one step,
- DL plans still move through their lifecycle.

That part does **not** disappear.
The benchmark contract does not replace the workflow mechanics.
It overlays them.

### In classical plans

The classical workflow remains:

- plan → execute → use

The difference is that execution now happens under a stored benchmark identity.

### In DL plans

The DL workflow remains:

- plan → train → validate → test → use

But benchmark-aware meaning becomes especially important around the evaluation-facing phases.
Train-only outputs are still not benchmark-final.
The benchmark contract matters most when the lifecycle reaches its evaluation results.

## Step 5 — Understand what reaches the results

This is the most important reason this document exists.

The benchmark contract does not stop at the run level.
It is propagated into results.

The result model is able to carry benchmark-facing fields such as:

- `benchmark_contract_id`
- `benchmark_mask_bank_id`
- `evaluation_support_fingerprint`
- `benchmark_realization_id`
- `shared_benchmark_parity`

That means a result can persist not only what algorithm ran and what metrics were produced, but also the benchmark identity under which those metrics were produced.

This is what makes the workflow practically valuable.
Without that propagation, the contract would remain mostly decorative.
With it, the result becomes comparison-ready in a much stronger way.

## What this changes for classical and DL results

The propagation logic is shared in spirit, but its meaning differs slightly depending on the route.

### Classical results

For classical results, benchmark attachment gives the one-step execution result an explicit shared benchmark identity.
The result is still operationally simple, but it is no longer isolated from the benchmark frame.

### DL validation and test results

For DL results, the benchmark context is especially meaningful once the evaluation phases produce outputs.
The benchmark identity then helps preserve the relationship between:

- the phase result,
- the contract,
- the realization,
- and the expected comparison cohort.

This matters later when comparison plans are built from multiple results.

## Why this matters for Comparison Studio

The whole point of shared benchmark attachment is not only better local execution hygiene.
It is also cleaner downstream comparison.

Because benchmark identity is persisted into results, later comparison tooling can work with richer comparison units instead of guessing compatibility from loose metadata.

That means `Experiment_Runs` is not just preparing execution.
In this workflow, it is also preparing comparison continuity.

## Recommended operator reading pattern

When you work with a benchmark-aware plan in `Experiment_Runs`, a good reading order is:

1. confirm the contract is attached in **Create Plan**,
2. confirm the plan saved with benchmark fields,
3. read **runtime truth**,
4. read **preflight**,
5. read **benchmark truth**,
6. only then execute,
7. then inspect the produced results with benchmark identity in mind.

This habit reduces confusion and makes it much easier to spot whether the run is truly operating under the intended contract.

## A practical mental model

A good way to understand this workflow is:

> a shared benchmark contract turns a normal run plan into a benchmark-identified run plan.

That does not change how the base algorithm family executes.
What it changes is the identity and governance carried by the plan and its results.
