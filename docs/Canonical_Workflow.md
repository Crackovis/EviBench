# ImputeBench — Canonical Workflow

This document describes the recommended working route in the **ImputeBench** module of
the EviBench platform. It focuses on the pages that form the most reliable end-to-end path
for preparing plans, executing them, inspecting results, and building structured comparisons.

The goal is simple: help you move through the product without guessing where the main
workflow really lives.

## CLI-first experiment orchestration

**Invariant: CLI builds and certifies; GUI reads and displays.**

The CLI is now the authoritative route for benchmark experiments.
Three command groups cover the full experiment lifecycle:

| Lane | CLI surface | Purpose |
|---|---|---|
| Temporal (classical + DL) | `imputebench temporal` | Recipe-book-driven temporal imputation |
| Spatio-temporal | `imputebench st` | Graph-driven spatio-temporal imputation |
| Dataset studies | `imputebench study` | Dataset characterization, missingness analysis, stationarity diagnostics |

### Quick start — temporal lane

```
python -m imputebench temporal recipe list
python -m imputebench temporal experiment run \
  --recipe-book official_londonaq_classical_benchmark \
  --tier smoke --algorithms mean --mask-families mcar --rates 0.3
```

### Quick start — spatio-temporal lane

```
python -m imputebench st experiment run --tier a --dataset-id london_aq
```

### Quick start — dataset studies

```
python -m imputebench study dataset profile --dataset-id london_aq
```

### Legacy commands

The old `imputebench run create/execute/status` commands remain available
for backward compatibility but are not the recommended route for official benchmarks.

## The recommended route at a glance *(GUI route — alternative for interactive inspection)*

```mermaid
flowchart LR
    A[Design recipe book] --> A2[Prepare core assets]
    A2 --> B[Create plan]
    B --> C[Execute plan]
    C --> D[Inspect results]
    D --> E[Build comparison]
    E --> F[Assemble thesis evidence]
    F --> G[Export or reuse evidence]
```

This is the clearest route through the product today.
It is the route to prefer when you want a workflow that is readable, repeatable, and easy to follow.

## Page roles in the workflow *(GUI route — alternative for interactive inspection)*

| Role | Pages | How to think about them |
| --- | --- | --- |
| Core workflow | `Experiment_Runs`, `Results_Navigator`, `Comparison_Studio`, `Settings` | These pages form the main operational route. |
| Setup & diagnostics | `Data_And_Algorithms`, `Resource_Ingestion`, `System_Readiness` | Use these when you need to prepare assets, import resources, or check diagnostics. |
| Thesis-grade | `Thesis_Evidence_Dashboard`, `Result_Storyboard`, `Evidence_Completeness_Gate` | Dashboard → Storyboard → Gate — the evidence export pipeline. |
| Specialized | `Wizard`, `Interactive_Lab`, `Figure_Factory`, `Analytics`, `Map_Alignment`, `Spatial_Simulation`, `Algorithm_Studio`, `Masking_Design` | These pages extend the product, but they are not required for the central route described here. |

The rest of this document focuses on the core workflow path. See
[`Thesis_Workflow.md`](Thesis_Workflow.md) for the thesis-grade evidence pipeline.

## Step 0 — Design recipe book (CLI-first)

**Recipe books** define experiment grids in declarative YAML. They specify which
algorithms, mask families, rates, realizations, and tiers belong in a benchmark
campaign. Built-in books provide official benchmarks. Clone to customize.

Recipe books define experiment grids in declarative YAML. Built-in books
provide official benchmarks. Clone a built-in book to customize for your
dataset or algorithm set:

```bash
# Discover built-in recipe books
imputebench experiment recipe list
imputebench experiment recipe show official_londonaq_classical_benchmark

# Clone and customize
imputebench experiment recipe clone official_londonaq_classical_benchmark --name my_benchmark
imputebench experiment recipe algorithm add my_benchmark --algorithm-id alg_brits
imputebench experiment recipe validate my_benchmark
```

Recipe books are registry-backed (SQLite). See
[Recipe_Book_Architecture.md](Recipe_Book_Architecture.md) for architecture
details and [`CLI_Reference.md`](CLI_Reference.md) for the full recipe command
reference.

## Step 1 — Prepare the minimum required assets

Before a plan can be executed, the ImputeBench module needs a small set of working assets:

- a dataset,
- one or more algorithms,
- at least one masking pattern.

The fastest way to prepare these records is usually through **Data & Algorithms** and, when needed, **Resource Ingestion**.

Use these pages to make sure the workbench has something concrete to run. Once the core assets exist, the main workflow moves to **Experiment Runs**.

## Step 2 — Create and execute plans in Experiment_Runs *(GUI route — alternative for interactive inspection)*

**Experiment Runs** is the operational center of the canonical workflow.
It is the place where saved plans are created, reviewed, selected, and executed.

This page is organized around three practical surfaces:

### Create Plan

Use this area to define a saved plan from the available dataset, algorithm, and masking assets.
A plan is a reusable execution configuration.
It describes what should be run before any result exists.

### Plan Manager

Use this area to review existing plans, inspect their status, and keep the working set readable.
It helps turn a growing collection of plans into something that stays manageable over time.

### Select & Execute

Use this area to choose the plan you want to run and launch execution.
This is also where operator-facing checks become important.

ImputeBench surfaces execution context directly in the page so the operator can see:

- what kind of execution was requested,
- what actually ran,
- which compute path is active,
- whether benchmark-related context is attached,
- and whether preflight checks reveal issues that should be addressed first.

In practice, this page is where the workflow moves from preparation into actual evidence generation.

Beyond the three main surfaces, **Experiment Runs** also provides:

- **Planning Assets** — manage benchmark contracts, mask banks, draft plans, and templates,
- **Planning Cockpit** — compact summary view for plan configuration,
- **Official Benchmarks** — thesis-grade benchmark preparation pipeline,
- **Action Center** — quick actions and experiment helpers for curated recipe books,
- **Targeted Runs** — focused execution on specific algorithm/dataset combinations.

See the detailed workflow documents for each execution class:
[`Experiment_Runs_Classical_Workflow.md`](Experiment_Runs_Classical_Workflow.md),
[`Experiment_Runs_DL_Workflow.md`](Experiment_Runs_DL_Workflow.md), and
[`Experiment_Runs_Benchmark_Contract_Workflow.md`](Experiment_Runs_Benchmark_Contract_Workflow.md).

## Step 3 — Inspect evidence in Results_Navigator

Once a plan has produced results, the next stop in the canonical route is **Results Navigator**.

This page is built for result reading rather than plan execution.
It helps you move from “something ran” to “what exactly happened, and what do the outputs show?”

It is organized around three main views:

### Browse

Use **Browse** to navigate the available results in a plan-aware way.
This is the fastest way to locate a result and understand where it belongs.

### Detail

Use **Detail** to inspect one result more carefully.
This is where metrics, artifacts, and visual analysis come together.
It is the right place to read a result as evidence rather than as a loose score.

### Compare

Use **Compare** when you want a quick result-to-result comparison directly from the navigator.
This is useful for immediate inspection, but more formal comparison work belongs in **Comparison Studio**.

Additional panels enrich the inspection experience:

- **Phase Pane** — navigate results by lifecycle phase (train / validate / test),
- **DL Cohort Panels** — cohort-specific views for deep-learning results,
- **Runtime Timing Panel** — per-phase execution timing measurements,
- **Best Loop Overview** — inspect the best checkpoint selection logic for DL results.

## Step 4 — Build structured comparisons in Comparison_Studio

After individual results have been inspected, **Comparison Studio** becomes the canonical place for formal comparison work.

This page treats comparison as a structured activity rather than a quick side-by-side view.
It is where comparison plans, benchmark assets, compatibility checks, and exported outputs come together.

The page is organized in two layers.

### Top-level areas

#### Comparison Plans

Use this area to open and manage saved comparison plans.

#### Benchmark Assets

Use this area to manage benchmark contracts and shared mask banks.
These assets help keep comparisons aligned when several results are meant to be read under the same benchmark logic.

#### New Comparison

Use this area to create a new comparison from selected results.

### Comparison workspace

Once a plan is open, the main workspace provides dedicated sections for:

- **Contract**
- **Compatibility**
- **Ranking**
- **Statistics**
- **Visual**
- **Export**
- **Caveats**
- **Actions**

Together, these sections turn comparison into a readable workflow: define the frame, verify that the comparison makes sense, inspect the outcomes, and export what needs to be reused.

For thesis-grade work, **Comparison Studio** also exposes:

- **Official Shell Panel** — manage official (thesis-bound) comparison materialization,
- **Materialization Diagnostics** — inspect why a comparison is or is not materialized,
- **Cohort Selection** — select result cohorts for batch operations,
- **Batch Plan Manager** — manage multiple comparison plans at once.

## Step 5 — Use Settings as operator support

**Settings** is not a destination in the workflow by itself, but it plays an important support role.

Use it when you need to check or change platform-wide behavior, especially around compute policy.
This is where GPU acceleration and effective runtime device choices are exposed in an operator-friendly way.

In other words, **Settings** supports the canonical workflow even though it is not one of its analytical stages.

## Step 6 — Thesis-grade evidence pipeline

Once comparisons are built and validated, the thesis workflow elevates them to
defensible, export-ready evidence. This path is covered in detail in
[`Thesis_Workflow.md`](Thesis_Workflow.md).

The three thesis pages form a pipeline:

| Step | Page | Purpose |
|---|---|---|
| 1 | **Thesis Evidence Dashboard** | Review evidence posture, identify gaps |
| 2 | **Result Storyboard** | Assemble scientific narrative from evidence |
| 3 | **Evidence Completeness Gate** | Final guardrail check before export |

## Supporting pages you may use when needed

Some pages are useful around the canonical route without being part of its core spine.

### Data_And_Algorithms

Use this page to create, inspect, edit, or clean the dataset and algorithm records used by plans.
It is usually part of initial setup and occasional maintenance.

### Resource_Ingestion

Use this page when you want to inspect a folder or archive and ingest it as a dataset, plugin, or result bundle.
It is especially useful when assets arrive from outside the current working registry.

### System_Readiness

Use this page when you need diagnostics.
It helps surface integrity issues, locality problems, workflow blockers, and cleanup tasks.
It is a support surface for restoring operational clarity when something feels off.

## Specialized pages outside the canonical route

ImputeBench also includes pages for guided use, exploration, visualization, or specialized spatial tasks.
These pages can be valuable in the right context, but they are not required to complete the main workflow described here.

That includes pages such as:

- `Wizard`
- `Interactive_Lab`
- `Figure_Factory`
- `Analytics`
- `Map_Alignment`
- `Spatial_Simulation`
- `Algorithm_Studio`
- `Masking_Design`

A simple rule helps here:
start with the canonical route first, then use specialized pages when a concrete need appears.
