# Procédure standard GitHub connector

Ce document sert de mémo opératoire pour travailler efficacement avec le connecteur GitHub via `api_tool` dans ce projet.

L’objectif est simple : éviter les tâtonnements de début de session, retrouver vite le bon dépôt, lire les bons fichiers, puis appliquer des modifications de manière fiable.

## 1. Réflexe de départ

Au début d’une tâche GitHub :

1. lister les ressources pour retrouver le tool GitHub exact ;
2. retrouver le dépôt visé ;
3. confirmer la base de travail avant toute modification.

Séquence recommandée :

- `api_tool.list_resources(path="", refetch_tools=true)`
- `search_installed_repositories_v2(query="Crackovis Experimentations")`
- si nécessaire `list_repositories(...)`
- `get_repo(repo_id)` si une confirmation d’identité est utile

## 2. Récupérer la bonne base de travail

Avant de créer une branche, identifier le dernier commit pertinent de `master`.

Approche recommandée :

- `search_commits(query="Merge pull request ...", repo="Crackovis/Experimentations")`
- prendre le commit de merge le plus récent comme base

But : ne pas repartir d’un ancien SHA devenu obsolète.

## 3. Créer une branche

Toujours travailler sur une branche dédiée.

Commande type :

- `create_branch(repository_full_name="Crackovis/Experimentations", branch_name="<nom-branche>", sha="<sha-master-récent>")`

Règle pratique :

- branche courte et explicite ;
- une branche par lot logique ;
- ne jamais patcher directement `master`.

## 4. Lire le code efficacement

Pour localiser puis lire le code utile :

- `search(repository_name="Crackovis/Experimentations", query="mot clé")`
- `fetch_file(repository_full_name="Crackovis/Experimentations", path="...", ref="master")`

Usage conseillé :

- `search(...)` pour repérer les fichiers pertinents ;
- `fetch_file(...)` pour lire le contenu réel d’un fichier exact.

## 5. Différence cruciale : nouveau fichier vs fichier existant

### Nouveau fichier

Pour un nouveau fichier, `create_file(...)` est généralement suffisant.

Bon cas d’usage :

- ajout d’une spec ;
- ajout d’un mémo ;
- ajout d’un document dans `docs/...`.

### Fichier existant

Pour modifier un fichier existant, éviter de s’appuyer sur `create_file(...)` comme méthode principale.

Le flux le plus fiable est :

1. `fetch_file(...)`
2. préparer le nouveau contenu
3. `create_blob(...)` pour chaque fichier modifié
4. `create_tree(...)`
5. `create_commit(...)`
6. `update_ref(...)`

C’est la procédure standard recommandée pour les patchs réels.

## 6. Procédure fiable pour patcher des fichiers existants

### Étape A — lire les fichiers

- `fetch_file(...)` sur tous les fichiers à modifier
- au besoin `search(...)` pour retrouver usages, appels, tests et dépendances

### Étape B — créer les blobs

- un `create_blob(...)` par fichier modifié

### Étape C — construire le tree

- `create_tree(repository_full_name=..., base_tree_sha="<commit-sha>", tree_elements=[...])`

Remarque importante :

Dans ce connecteur, `base_tree_sha` peut être alimenté en pratique par le **commit SHA courant**. C’est la méthode la plus simple à réutiliser ici.

### Étape D — créer le commit

- `create_commit(repository_full_name=..., message="...", tree_sha="...", parent_sha="<commit-sha>")`

### Étape E — avancer la branche

- `update_ref(repository_full_name=..., branch_name="...", sha="<nouveau-commit>")`

### Étape F — vérifier

- `fetch_commit(repo_full_name="Crackovis/Experimentations", commit_sha="...")`
- éventuellement `compare_commits(base="...", head="...")`

## 7. Procédure standard complète

Quand il faut corriger du code dans le dépôt :

1. retrouver le repo ;
2. retrouver les fichiers ;
3. identifier le dernier commit de base ;
4. créer la branche ;
5. lire les fichiers exacts ;
6. préparer les nouveaux contenus ;
7. créer les blobs ;
8. créer le tree ;
9. créer le commit ;
10. avancer la ref de branche ;
11. vérifier le commit final.

## 8. Gestion de l’erreur “Update is not a fast forward”

Cette erreur signifie que la branche a bougé entre la création du commit et l’update de la ref, ou que le parent utilisé n’était plus le bon.

Réaction correcte :

- soit recréer le commit depuis le dernier HEAD de la branche ;
- soit utiliser `update_ref(..., force=true)` **uniquement** si l’on sait qu’il s’agit de notre branche de travail et que le déplacement est volontaire.

Règle pratique :

- `force=true` acceptable sur une branche personnelle de correction ;
- à éviter pour `master`.

## 9. Vérifications utiles après patch

Après un changement :

- lire le commit avec `fetch_commit(...)` ;
- vérifier le diff ;
- vérifier que les bons fichiers ont été modifiés ;
- vérifier que le message de commit décrit bien le lot.

## 10. Commandes les plus utiles

### Retrouver le dépôt

- `search_installed_repositories_v2(...)`
- `list_repositories(...)`

### Trouver du code

- `search(repository_name="Crackovis/Experimentations", query="...")`

### Lire un fichier

- `fetch_file(...)`

### Vérifier un commit

- `fetch_commit(...)`

### Comparer deux états

- `compare_commits(...)`

### Créer une branche

- `create_branch(...)`

### Ajouter un nouveau fichier

- `create_file(...)`

### Modifier de l’existant

- `create_blob(...) -> create_tree(...) -> create_commit(...) -> update_ref(...)`

## 11. Anti-patterns à éviter

- commencer à modifier avant d’avoir identifié le bon repo ;
- repartir d’un SHA ancien ou ambigu ;
- utiliser `create_file(...)` comme méthode par défaut pour éditer de l’existant ;
- multiplier les micro-commits quand un seul lot logique suffit ;
- oublier de relire le commit final ;
- oublier que la branche peut avoir bougé entre-temps.

## 12. Checklist ultra-courte

```text
Repo -> Files -> Base commit -> Branch
fetch_file
create_blob x N
create_tree(base_tree_sha=commit_sha)
create_commit(parent_sha=commit_sha)
update_ref(branch)
fetch_commit
```

## 13. Règle de travail recommandée pour ce projet

Dans `Crackovis/Experimentations`, la séquence à privilégier est :

- repo exact ;
- lecture ciblée ;
- branche dédiée ;
- patch via blobs/tree/commit/ref ;
- vérification finale systématique.

Cette procédure doit être considérée comme le mode opératoire standard pour les prochaines sessions GitHub liées au module ImputeBench d'EviBench et au dépôt Experimentations.
