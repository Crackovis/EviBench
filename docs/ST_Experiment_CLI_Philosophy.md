# ST Experiment CLI Philosophy

How the EviBench spatio-temporal (ST) experiment lane is launched, certified, and documented — and how to replicate the same CLI-first pattern for future lanes.

> **Scope note.** This document describes the ST experiment CLI **exactly as implemented** in `imputebench/cli/st_cmd.py` and `imputebench/services/spatiotemporal/`. It was written after the ST scientific lane had been implemented; it documents the current system, not its development history. Every command below has been verified against the local CLI (`--help`) or its source.

---

## 1. What CLI-first means for the ST lane

The single invariant that governs the entire lane:

> **CLI builds and certifies. GUI reads and displays.**

Concretely:

- The CLI (`imputebench st …`) is the **orchestration authority**. It builds graph assets, mask banks, plans, runs, metrics, evidence packs, gate reports, and the official campaign certification.
- Services in `imputebench/services/spatiotemporal/` implement all behavior **behind** the CLI. They have no Streamlit or GUI dependency.
- Any GUI or dashboard layer is a **reader**: it consumes the materialized registry, exported JSON/CSV/Markdown evidence, and gate reports. It must never redefine recipe grids, corrected variants, mask scenarios, or orchestration logic, and it is never the source of truth for experiment construction.

Why CLI-first:

- **Reproducibility** — every asset carries fingerprints (graph, mask support, plan); the same command reproduces the same artifacts.
- **Scriptability** — the full campaign is one command, not a sequence of UI clicks (`st experiment run` replaces a 17-step manual runbook).
- **Resume behavior** — `--skip-completed` makes re-launching after interruption safe and cheap.
- **Auditability** — JSONL event logs, JSON progress files, DB audits, and export audits leave a verifiable trail.
- **Headless execution** — long GPU campaigns run without any UI session.
- **Public documentation clarity** — commands and outputs can be documented and verified literally.
- **Future lane replication** — the pattern (recipes → assets → plans → runs → evidence → gates → certification) transfers to other lanes (see Section 7).

---

## 2. Core concepts

All concepts below are implementation terms with concrete homes in the codebase.

| Concept | What it is in the implementation |
|---|---|
| **Recipe book** | The authoritative recipe collection `official_londonaq_st_benchmark`. **As of v0.3.0, the recipe book is registry-backed** (SQLite) with a declarative YAML definition. The registry is the single source of truth consumed by both CLI and GUI. `builtin_recipes.py` is a thin facade. Sourced from the lane2 markdown pack under `docs/assets/utils/experiments/lane2_spatiotemporal_londonaq/`. See [Recipe_Book_Architecture.md](Recipe_Book_Architecture.md). |
| **Recipe** | One `STRecipeDefinition`: dataset, algorithms, corrected variants, mask scenario + rate, realization count, seeds, graph policy, training tier, epochs, metrics, expected outputs. The materialized registry currently holds 15 recipes (6 Tier A, 9 Tier B). |
| **Tier** | Experiment scale/intent: `smoke`, `calibration`, `tier_a` (A), `tier_b` (B), `graph_sensitivity` (recipe tiers); `st experiment run --tier` accepts `smoke|a|b|calibration`. Distinct from the **training tier** (`smoke` 1–2 epochs, `diagnostic` 3–10, `scientific` ≥ 50, recommended 100). |
| **Graph policy** | A named graph construction rule: `grid_4n_v1`, `grid_8n_v1`, `distance_knn_v1`, `correlation_train_v1` (train-split-only correlation, scientific), `correlation_full_v1` (full-dataset correlation, **exploratory only** — it never passes the `train_only_correlation_graph_ready` gate). |
| **Graph asset** | A persisted, fingerprinted graph: `adjacency.npy`, `node_mapping.json`, `graph_metadata.json`, `graph_fingerprint.json` under `data/benchmark_graphs/official_londonaq/<policy>/`. Identified by a `graph_id`. |
| **Mask bank** | A graph-aware bank of evaluation masks for one (dataset, mask family, rate), carrying `graph_fingerprint`, `hidden_support_fingerprint`, `split_fingerprint`, and `eligibility_fingerprint`. Created per graph policy × family. |
| **Realization** | One independently seeded mask draw inside a bank. Official banks carry 5 shared realizations, so every algorithm sees identical missingness. |
| **Materialization** | `st recipe materialize` writes the canonical machine-readable registry (recipes, tiers, profiles, execution order, schema, checksums, manifest) to `docs/assets/utils/experiments/lane2_spatiotemporal_londonaq/recipes/`. `verify-materialization` re-checks integrity, counts, and the schema contract. |
| **Plan generation** | `STPlanService.create_plans` (CLI: `st plan create`, or implicitly via `st experiment run`) binds a recipe tier to a shared `graph_id` and mask bank ids and creates `ExperimentRun` rows plus benchmark contracts. |
| **ExperimentRun container** | One database `ExperimentRun` per (algorithm × mask family) under one graph policy. A *container*, not a single evaluation: it executes every realization in its bank. |
| **Evaluation cell** | One (algorithm × mask family × realization) result with its own metrics and prediction artifacts. **24 containers × 5 realizations = 120 official Tier-A evaluation cells** (4 algorithms × 6 mask families = 24 containers). |
| **Execution orchestration** | `STExperimentOrchestrator.run()` — graph → mask → plan → execute → (evidence), with skip-completed, event log, progress file, train-config overrides, and post-run training-record persistence. |
| **Evidence export** | `STEvidenceExportService` and companions write the Chapter 06 evidence pack (`docs/exports/thesis/chapter06/`, subdirectories `00_st_audit_snapshot` … `09_scientific_gate`). |
| **Gate evaluation** | `STGateService` (CLI: `st gate --profile <name>`) evaluates 17 readiness profiles and persists JSON verdicts. |
| **Scientific readiness** | The SCI-FIX08 evidence profile plus the SCI-FIX09 final gate (`st scientific gate report`), which decides whether **bounded** EviBench ST benchmark claims are allowed. |
| **Official campaign certification** | `st experiment certify-official` verifies, from the metadata DB and reports, that the completed containers constitute the full 120-cell official Tier-A campaign, and writes the canonical campaign report. |

The four official algorithms run as **corrected variants**: `stgcn → stconv_v1`, `grin → mpgru_v1`, `ignnk → dgc_kriging_v1`, `dcrnn → dcgru_reconstruction_v1`. These are bounded benchmark implementations — the benchmark does **not** claim paper-faithful reproduction of the original architectures.

## 3. Full lifecycle

The implemented lifecycle, end to end. Steps 1–7 are bundled by `st experiment run`; each is also available as an individual command.

### 3.1 Preflight validation
- **Purpose:** fail fast before plan creation/execution.
- **Command:** `imputebench st preflight --dataset-id london_aq --graph-id <graph_id>`
- **Service:** `STPreflightService.evaluate`
- **Inputs:** dataset id, persisted `graph_id`, graph output dir.
- **Outputs:** JSON with checks `dataset_loads`, `source_shape` ([600, 10, 14, 4]), `graph_asset_loads`, `adjacency_shape`, `tensor_adapter_shape`, `st_plugins_registered`, `st_executor_wired`, `sqlite_schema_version`; status `PASS`/`BLOCKED`.
- **Failure modes:** dataset not resolvable; graph asset missing; ST plugins not registered; stale DB schema.

### 3.2 Dataset tensor resolution
- **Purpose:** load the LondonAQ tensor `[T, rows, cols, F]` and resolve the dataset identifier (UUID, name, or slug like `london_aq`).
- **Command:** implicit in `st experiment run` (phase 1/5); inspect via `st tensor inspect --dataset-id london_aq --graph-id <graph_id>`.
- **Service:** `DatasetService.load_array` + `LondonAQGraphTensorAdapter.to_graph_tensor` (reshapes to `[T, N, F]`, N = 140).
- **Failure modes:** `Dataset not found: …` with the list of available datasets.

### 3.3 Graph construction
- **Purpose:** build and persist fingerprinted graph assets per policy.
- **Command:** `imputebench st graph build --dataset-id london_aq --policy correlation_train_v1`
- **Service:** `GraphBuilderService.build` → `GraphAssetStore`.
- **Inputs:** policy, `--knn-k` (distance_knn), `--corr-threshold` (0.7 default), `--train-end` / `--split-id` (correlation policies).
- **Outputs:** `adjacency.npy`, `node_mapping.json`, `graph_metadata.json`, `graph_fingerprint.json`; idempotent — an identical fingerprint returns the existing asset unless `--force`.
- **Failure modes:** `correlation_train_v1` **refuses to run without valid train-split metadata** (no silent full-dataset fallback); fingerprint mismatch with an existing asset.

### 3.4 Mask bank creation
- **Purpose:** generate shared graph-aware evaluation masks.
- **Command:** `imputebench st mask-bank create --dataset-id london_aq --family spatial_block --rate 0.3 --realizations 5 --graph-id <graph_id>`
- **Service:** `STMaskBankService.create_graph_aware_bank`.
- **Outputs:** bank row + artifacts under `data/benchmark_mask_banks/official_londonaq/st/`, with graph/support/split/eligibility fingerprints.
- **Failure modes:** missing graph asset; unsupported family (allowed: `mcar`, `mar`, `mnar`, `spatial_block`, `sensor_dropout`, `node_holdout`).

### 3.5 Recipe resolution / materialization
- **Purpose:** validate the recipe book and publish the canonical machine-readable registry.
- **Commands:** `st recipe validate`, `st recipe list`, `st recipe inspect --recipe-id <id>`, `st recipe plan --profile tier_a` (dry-run only), `st recipe materialize`, `st recipe verify-materialization`.
- **Services:** `STRecipeBookService`, `STRecipeMaterializationService`.
- **Outputs:** readiness report in `docs/exports/thesis/chapter06/00_st_recipe_book/`; registry JSON files (recipes/tiers/profiles/execution order/schema/checksums/manifest) under the lane2 `recipes/` directory.
- **Failure modes:** missing required source markdown files; schema/checksum mismatch (`verify-materialization` exits 1 when status ≠ `materialized`).

### 3.6 Plan generation
- **Purpose:** turn a tier into concrete `ExperimentRun` containers bound to one graph and per-family mask banks.
- **Command:** `imputebench st plan create --recipe official_londonaq_st_benchmark --tier A --dataset-id london_aq --graph-id <graph_id> --mask-bank mcar=<bank_id> …`
- **Service:** `STPlanService.create_plans`.
- **Outputs:** created runs + benchmark contracts, bound to the graph fingerprint.
- **Failure modes:** missing bank mapping for a family; unknown tier.

### 3.7 Experiment execution
- **Purpose:** execute every container (each container runs all realizations of its bank).
- **Commands:** `st experiment run` (full pipeline) or `st run execute --run-id <id>` (single container, with ST-specific precondition checks: spatiotemporal execution class, graph asset present, contract and bank ids set, algorithms registered as `family=spatiotemporal`).
- **Service:** `STExperimentOrchestrator.run` → `ExperimentRunner.execute`.
- **Outputs:** per-cell results in the DB; prediction artifacts under `data/artifacts/st_predictions/<run_id>/`; for scientific-tier runs a training record under `data/st_scientific_training/<algorithm>/<variant>/`.
- **Failure modes:** plugin errors (recorded per run in the report and event log; the campaign continues), CUDA issues (check `st env` first).

### 3.8 Metric and artifact persistence
- **Purpose:** persist MAE/RMSE metrics, predictions, training history, runtime/device metadata per evaluation cell.
- **Command:** automatic during execution; audit afterwards with `st audit db --tier A`.
- **Failure modes:** missing artifacts surface later as certification blockers — they never silently pass.

### 3.9 Evidence export
- **Purpose:** write the Chapter 06 evidence pack.
- **Commands:** `st evidence export` (full pack), `st evidence export --profile st_scientific_evidence_v1` (SCI-FIX08 profile), `st compare --lot within_st`, `st figures generate`, `st evidence audit`, `st evidence visual-audit`, `st evidence mirror --thesis-root <dir>`.
- **Services:** `STEvidenceExportService`, `STScientificEvidenceExportService`, `STComparisonService`, `FigureGalleryService`, `Chapter06MirrorService`.
- **Outputs:** `docs/exports/thesis/chapter06/00…09` subdirectories (audit snapshot, graph characterization, spatial missingness, algorithm lifecycle, comparisons, storyboards, gates, figures, SCI-FIX08 profile, SCI-FIX09 gate).
- **Note:** `st experiment run` auto-runs comparisons, evidence export, and the `comparison_ready`/`thesis_ready` gates after a completed campaign unless `--no-evidence` is passed.

### 3.10 Gate evaluation
- **Purpose:** convert evidence into explicit pass/blocked verdicts per readiness profile.
- **Commands:** `st gate --profile <one of 17 profiles>`; `st scientific gate report` (SCI-FIX09 final gate); `st training adequacy report`; `st training convergence report`; `st graph sensitivity report` (optional SCI-FIX07).
- **Outputs:** JSON/Markdown/CSV reports under `06_st_gates/` and `09_scientific_gate/`.
- **Failure modes:** a *blocked* gate before reruns is **correct behavior**, not a bug — blockers list exactly what evidence is missing.

### 3.11 Official campaign certification
- **Purpose:** verify the completed containers constitute the full official Tier-A campaign and write the canonical campaign status artifact.
- **Command:** `st experiment certify-official` (see Section 6).
- **Failure modes:** exits 1 with explicit blockers when containers/cells/metrics/artifacts are incomplete.

### 3.12 README / report regeneration
- **Purpose:** keep the evidence pack self-describing.
- **Commands:** `st chapter06-readme` (refresh the chapter06 root README from live JSON); `st regenerate-chapter06` (one-shot 11-step regeneration of the full pack: tests → comparisons → training adequacy → convergence → evidence export → algorithm cards → SCI-FIX08 → gates → SCI-FIX09 → mirror → README; `--clean` wipes auto-generated subdirs but **never** touches `00_st_recipe_book/`).

## 4. Key design invariants

Each invariant below is verified against the implementation.

1. **Deterministic, fingerprinted assets.** Graph assets carry adjacency/node-mapping/graph fingerprints; mask banks carry hidden-support, split, and eligibility fingerprints; plans bind to graph fingerprints; certification checks a plan fingerprint binding.
2. **Idempotent builds.** `st graph build` returns the existing asset on fingerprint match (use `--force` to rebuild). `st recipe materialize` is re-runnable (`--overwrite` defaults on).
3. **Safe resume.** `st experiment run --skip-completed` skips any run that already has a `COMPLETED` result and logs a `skipped` event.
4. **JSONL event logging.** `--event-log` appends one event (`completed`/`failed`/`skipped`) per run with timestamp, run id, and index.
5. **Progress file tracking.** `--progress-file` rewrites a JSON summary (`completed`/`skipped`/`failed`/`total`/`current_idx`) after every run.
6. **Train-only graph construction for scientific claims.** `correlation_train_v1` derives edges from the train split only (default 60/20/20 boundary, override with `--train-end`) and errors out rather than falling back to the full dataset. `correlation_full_v1` is explicitly exploratory and gated out.
7. **Shared mask support.** All algorithms in a cell consume identical mask realizations from the same bank; cells with mismatched support fingerprints are never compared (graph-policy sensitivity groups by support key).
8. **Plugin family enforcement.** `st run execute` refuses runs whose algorithms are not registered with `family=spatiotemporal`, and refuses non-ST runs outright.
9. **No GUI dependency in services.** ST services import no Streamlit; GUI layers read materialized/exported files.
10. **Post-run evidence regeneration.** Evidence, comparisons, and gates are regenerated from persisted data at any time (`st regenerate-chapter06`); evidence is derived, never hand-maintained.
11. **Gate-based claim readiness.** Claims are allowed only via gate verdicts; the SCI-FIX09 domain model hard-codes permanently blocked claims (universal superiority, state-of-the-art, deployment generalization, paper reproduction, paper-faithful, unvalidated unseen-graph transfer).
12. **Official campaign status is separate from calibration readiness.** The SCI-FIX09 report carries distinct fields for each (Section 6) — a passing calibration gate never implies the official campaign ran.
13. **Reset is explicit and scoped.** `st experiment reset [run|mask|graph|all] --dry-run` previews deletions; nothing else deletes campaign assets.

## 6. Official campaign and certification

### Launch completion ≠ thesis-ready certification

Finishing `st experiment run` only means the runner executed the plan. Certification additionally requires that, in the database and on disk: all expected containers are `COMPLETED`, all expected cells have MAE/RMSE metrics and prediction artifacts, fingerprints bind cells to the plan, the graph policy is `correlation_train_v1`, epochs = 100 with early stopping enabled, and training adequacy/convergence are acceptable. `st experiment certify-official` checks all of this **without rerunning anything or modifying the database**, then writes the canonical campaign status artifact:

```text
docs/exports/thesis/chapter06/00_st_recipe_book/
  ST_RUN00_PHASE_C_TIER_A_OFFICIAL_REPORT.json   ← canonical status source
  ST_RUN00_PHASE_C_TIER_A_OFFICIAL_REPORT.md
  ST_RUN00_PHASE_C_TIER_A_OFFICIAL_CONTAINERS.csv
  ST_RUN00_PHASE_C_TIER_A_OFFICIAL_CELLS.csv
```

The SCI-FIX09 gate (`st scientific gate report`) consumes this canonical report as its official-campaign status source, so claim readiness is always derived from the written artifact, never from memory of having run something.

### Containers vs. evaluation cells

The official Tier-A campaign is:

```text
4 algorithms × 6 mask families = 24 ExperimentRun containers
24 containers × 5 realizations = 120 official evaluation cells
```

Counting containers as cells (or vice versa) is the most common way to misread campaign status. Certification validates both counts independently (`--expected-containers 24 --expected-cells 120`).

### Calibration readiness vs. official campaign readiness

The SCI-FIX09 report (`STScientificGateReport` in `imputebench/domain/spatiotemporal/scientific_gate.py`) carries four distinct status fields:

| Field | Meaning |
|---|---|
| `calibration_scientific_ready` | The calibration-phase infrastructure (Phase B) passed the scientific gate — the pipeline is scientifically sound. |
| `official_campaign_launched` | The official Phase C campaign was actually started. |
| `official_tier_a_campaign_complete` | All 120 official Tier-A evaluation cells were executed and verified. |
| `official_tier_a_ready_for_thesis` | Thesis-level Tier-A evidence is available. |

A gate can report `calibration_scientific_ready: true` while the official campaign is incomplete — that combination is meaningful, not contradictory. Documentation and claims must always state **which** readiness they refer to.

As of the canonical report generated on 2026-05-20, the Phase C Tier-A campaign is certified: all four fields above are `true`, with 24/24 containers and 120/120 cells complete.

### Post-certification regeneration

After certification, refresh the downstream reports so they consume the new status:

```bash
python -m imputebench st scientific gate report
python -m imputebench st gate --profile scientific_ready
python -m imputebench st chapter06-readme
```

### Claim boundaries

Even with every gate passed, the implementation permanently blocks these claims (`PERMANENTLY_BLOCKED` in the SCI-FIX09 domain model): universal algorithm superiority, state-of-the-art claims, deployment generalization, paper result reproduction, paper-faithful claims, and unseen-graph transfer (unless separately validated). What passing gates allow are **bounded** claims: controlled comparisons and metric summaries under the stated dataset, masks, graph policy, and training conditions. In particular, any "graph-aware models help" statement is bounded to this benchmark's conditions and requires the graph-policy sensitivity caveats.

## 7. How to replicate the pattern for a new lane

A developer blueprint for building, e.g., a temporal experiment lane with the same architecture.

1. **Create a CLI group.** New module `imputebench/cli/<lane>_cmd.py` exposing a Click group; register it in `imputebench/cli/__init__.py` (`cli.add_command(...)`). Mirror the ST sub-groups: asset construction, supports/mask banks, recipes (dry-run only), plans, experiment lifecycle, evidence, gates.
2. **Define domain contracts first.** Frozen dataclasses with `to_dict()`, a `POLICY_VERSION` constant, and `__all__` exports under `imputebench/domain/<lane>/` — recipe book, asset contracts, readiness/gate report models. Put fingerprints in the contracts from day one.
3. **Author recipes as docs + machine registry.** Keep human-readable recipe markdown as the source, validate it (`recipe validate`), and materialize a checksummed machine-readable registry (`recipe materialize` / `verify-materialization`). The registry — not the GUI, not ad-hoc scripts — is what planning consumes.
4. **Generate shared evaluation supports.** The lane's equivalent of mask banks: seeded, fingerprinted, shared across all algorithms, with the realization count fixed in the recipe.
5. **Materialize plans before executing.** A plan service that creates run containers + contracts bound to asset fingerprints, plus a dry-run path (`recipe plan`) that prints the full matrix without touching the DB.
6. **Orchestrate execution in one command.** An orchestrator service with phases, progress callback, `--skip-completed` resume, JSONL `--event-log`, and a `--progress-file`; the CLI command is thin and delegates everything.
7. **Export evidence as derived data.** Evidence services read the DB/artifacts and write JSON/CSV/Markdown packs; never hand-edit evidence. Provide a one-shot `regenerate-*` command.
8. **Write gates, not prose.** Each readiness question becomes a gate profile returning passed/blocked with explicit blocker strings. Pre-rerun "blocked" is correct output. Separate calibration readiness from official-campaign status in the report model.
9. **Document from the implementation.** Command reference from `--help`, lifecycle from the orchestrator, concepts from the domain models — in that order.
10. **Keep the GUI a reader.** Any UI consumes the materialized registry and exported reports, or shells out to the CLI. It never constructs experiments.

**Design sketch (not implemented)** — what a future temporal lane launch could look like:

```bash
python -m imputebench temporal experiment run \
  --tier a \
  --dataset-id london_aq \
  --mask-families mcar,mar,mnar \
  --realizations 5 \
  --epochs 100 \
  --skip-completed \

```

This command does not exist today; it illustrates the target shape only. (The existing temporal lanes currently use `scripts/prepare_official_experiments.py` and the run manager — see `docs/assets/utils/experiments/CLI_PREPARATION_GUIDE.md`.)

## 8. Troubleshooting

| Symptom | Probable cause | How to inspect | How to fix |
|---|---|---|---|
| `Dataset not found: 'london_aq'` | Dataset not registered, or slug doesn't match name/tags | `python -m imputebench dataset list` | Register/ingest the dataset; the resolver accepts UUID, exact name, name tokens, or tag |
| `Graph asset not found` / `No graph asset with graph_id=…` | Graph never built, or wrong `--graph-output-dir` | `python -m imputebench st graph list` | `st graph build --dataset-id london_aq --policy <policy>` |
| Graph build error for `correlation_train_v1` about train split | Train-end boundary out of range — the policy refuses full-dataset fallback | Read the error; it prints the valid range | Pass a valid `--train-end`, or accept the default 60% boundary |
| Graph policy mismatch at certification | Cells were produced under a non-official policy | `st audit db --tier A`; certification blockers | Rerun affected containers under `correlation_train_v1` |
| Mask bank missing at plan creation | Bank not created for that (policy, family, rate) | `st experiment reset mask --dry-run` lists banks; check `data/benchmark_mask_banks/…` | `st mask-bank create …`, or let `st experiment run` create banks itself |
| `Algorithm … is not registered as family=spatiotemporal` | Plugin not registered or wrong family | `python -m imputebench algorithm list`; `st preflight` (`st_plugins_registered`) | Register the plugin; verify its manifest family |
| Run skipped unexpectedly | `--skip-completed` found an existing `COMPLETED` result | Event log shows `"event": "skipped"` | Intentional. To force re-execution: `st experiment reset run --dry-run` first, then without `--dry-run` |
| Event log file absent | `--event-log` not passed (it is opt-in) | — | Pass `--event-log data/logs/<name>.jsonl` (parent dirs are created automatically) |
| Progress file stale | Reading a file from an older launch | Check `current_idx`/`total` against the live console | Use the `--progress-file` path of the *current* launch; the file is rewritten after every run |
| Gate says calibration ready but official campaign incomplete | Correct, distinct semantics (Section 6) | `09_scientific_gate/SCIENTIFIC_GATE_REPORT.json` — compare the four status fields | Run/finish the official campaign, then `st experiment certify-official` |
| README claims campaign-scale results but official report missing | Chapter06 README regenerated before certification | Check `00_st_recipe_book/ST_RUN00_PHASE_C_TIER_A_OFFICIAL_REPORT.json` exists | `st experiment certify-official`, then `st chapter06-readme` |
| Certification fails: cells/metrics/artifacts missing | Incomplete containers, failed cells, or deleted artifacts | Blocker list in the certify output; `st audit db --tier A` | Re-launch with `--skip-completed` to fill gaps; never hand-edit reports |
| CUDA not used / out-of-memory | Wrong interpreter or CPU-only torch build | `st env` | Install a CUDA torch build in the active environment; the orchestrator empties the CUDA cache between runs |
