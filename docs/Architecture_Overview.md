# Architecture Overview

EviBench follows a **Domain-Driven Design (DDD)** architecture organised in four
layers. This document explains the key design invariants that govern the codebase
— useful for contributors, advanced users, and anyone who needs to understand how
the platform is built.

---

## Layer structure

```
domain → application → infrastructure → adapters (cli / api / view)
```

| Layer | Location | Responsibility |
|---|---|---|
| **Domain** | `imputebench/domain/` | Core models, semantics, contracts. No framework dependencies. |
| **Application** | `imputebench/application/` | Use cases, command bus, queries. Orchestrates domain objects. |
| **Infrastructure** | `imputebench/services/`, `imputebench/storage/` | Service implementations, SQLite persistence, file I/O. |
| **Adapters** | `imputebench/cli/`, `app/pages/` | CLI commands, Streamlit views. Thin translation layers. |

**Forbidden dependency direction** : `domain → Streamlit`, `domain → SQLite`,
`view → MetadataStore.create()`.

---

## Five architecture invariants

These rules were established in FT00 and are enforced by automated guard tests.

### 1. Pages render; they do not decide

Streamlit pages dispatch commands and display results. They never contain
business logic, create services directly, or modify the domain model.

```python
# ✅ Correct — page receives pre-built services
wb = build_comparison_studio_services()
svc = get_studio_service(wb)

# ❌ Incorrect — page creates a service directly
store = MetadataStore()
```

Guard test: `tests/architecture/test_no_streamlit_in_domain.py`

### 2. Only the composition root builds services

All services are constructed once in `app/service_composition/core_graph.py`
(`WorkbenchCoreGraph`) and injected into page bundles via `page_bundles.py`.
No service instance is duplicated across pages.

```
WorkbenchCoreGraph (built once, Streamlit-cached)
    └── page_bundles.py (slices the graph per page)
        └── page.py (receives only what it needs)
```

Guard test: `tests/architecture/test_no_store_create_outside_composition.py`

### 3. Legacy façades are not canonical

The `ComparisonEngine` class is a compatibility bridge only. The canonical
comparison path uses `ComparisonStudioServices` exposed through
`studio_comparisons` and `comparison_app`.

```python
# ✅ Canonical path
from app.pages.results.comparison_studio.service_access import (
    get_studio_service,
    get_comparison_app,
)

# ⚠️ Legacy — still functional but not the canonical path
# ComparisonEngine.studio_service()
```

Guard test: `tests/architecture/test_no_comparison_engine_in_comparison_studio.py`

### 4. Domain semantics are centralized

Result identity, comparison eligibility, family scope, and phase normalization
are resolved in exactly one place: `imputebench/domain/results/`.

| Module | Responsibility |
|---|---|
| `semantics.py` | `ResultSemantics` — canonical truth about a result |
| `eligibility.py` | `ComparisonEligibility` — whether two results can be compared |
| `eligibility_policy.py` | Policy rules for eligibility decisions |
| `family_scope.py` | Algorithm family membership |
| `phase_normalization.py` | Lifecycle phase name normalization |
| `descriptor.py` | `ResultDescriptor` — observable properties of a result |
| `lifecycle.py` | `ExecutionLifecycle` — plan → train → validate → test → use |

Guard test: `tests/architecture/test_no_semantic_dict_rederivation_in_pages.py`

### 5. CLI / API / View parity is mandatory

Every non-trivial UI action maps to a registered command. The command registry
(`COMMAND_REGISTRY`) ensures that CLI, API, and View paths execute the same
underlying logic.

```
User action in page
    → ComparisonViewDispatch
        → ApplicationService
            → Domain service
                → Infrastructure
```

Guard test: `tests/architecture/test_command_parity_registry.py`

## Read Models

The `imputebench/read_models/` layer (60+ files) provides pre-computed,
UI-optimised views of domain data. Each read model is purpose-built for a
specific page surface:

| Read Model | Serves |
|---|---|
| `results_navigator_page.py` | Results Navigator — Browse tab |
| `comparison.py`, `comparison_actions.py`, `comparison_candidates.py` | Comparison Studio |
| `operational_label.py`, `operational_navigator.py` | Platform-wide label rendering |
| `evidence_completeness_gate.py` | Evidence Completeness Gate |
| `result_storyboard.py` | Result Storyboard |
| `thesis_evidence_dashboard.py` | Thesis Evidence Dashboard |
| `runtime_trace.py`, `runtime_timing.py` | Execution runtime views |

Read models are never imported by domain or application code — only by adapters.

---

## Operational Labels

Every operator-facing object (dataset, algorithm, run, result, benchmark
contract) follows a platform-wide naming contract defined in
[`Operational_Labels.md`](Operational_Labels.md).

Key rule: **raw IDs are hidden in normal mode** and surfaced only in
technical/debug mode. Labels are always resilient — they never raise exceptions
on missing references.

## Guard tests

The architecture is defended by automated tests that fail the build when
invariants are violated:

| Test | Invariant |
|---|---|
| `test_no_streamlit_in_domain.py` | #1 — Pages render, don't decide |
| `test_no_store_create_outside_composition.py` | #2 — Composition root only |
| `test_no_comparison_engine_in_comparison_studio.py` | #3 — Legacy façades not canonical |
| `test_no_semantic_dict_rederivation_in_pages.py` | #4 — Semantics centralized |
| `test_command_parity_registry.py` | #5 — CLI/API/View parity |
| `test_comparison_studio_actions_no_raw_studio_methods.py` | FT07 — View dispatch bridge |
| `test_no_default_heavy_load_in_navigation.py` | FT09 — Lazy loading |
| `test_cli_no_scattered_store_creation.py` | FT12 — CLI adapter scaffolding |
| `test_command_registry_adapter_refs.py` | FT12 — Adapter references |
| `test_no_registry_list_in_pages.py` | Legacy registry isolation |

Run with:

```bash
pytest tests/architecture/ -v
```
