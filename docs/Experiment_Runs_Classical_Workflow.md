## CLI-first classical orchestration

The canonical route for classical temporal experiments is now:

```
python -m imputebench temporal experiment run \
  --recipe-book official_londonaq_classical_benchmark \
  --tier a --dataset-id london_aq \
  --algorithms mean,median,locf,linear,knn \
  --mask-families mcar,mar,mnar \
  --rates 0.1,0.3,0.5 \
  --realizations 5 \
  --execution-class classical \
  --skip-completed
```

This single command:
- Resolves the official classical recipe book
- Filters to selected algorithms, mask families, and rates
- Materializes mask banks, benchmark contracts, and experiment plans
- Executes classical imputation (fit + impute + metrics)
- Writes event logs and progress files
- Skips already-completed runs (idempotent)

### Smoke run (quick validation)

```
python -m imputebench temporal experiment run \
  --recipe-book official_londonaq_classical_benchmark \
  --tier smoke --algorithms mean --mask-families mcar --rates 0.3 \
  --realizations 1 --execution-class classical
```

### ARMA plugin

ARMA is available as a classical plugin candidate once registered:
```
python -m imputebench plugin register arma
python -m imputebench temporal experiment run \
  --recipe-book official_londonaq_classical_benchmark \
  --algorithms arma --study-preflight stationarity
```

### Legacy route

The old `imputebench run create` + `imputebench run execute` commands still work
for ad-hoc single runs but are not the recommended route for official benchmarks.

## GUI route (alternative for interactive inspection)

# Experiment Runs — Classical Workflow

This document describes the recommended use of **Experiment Runs** for the simplest operational case:

- classical algorithms,
- no deep-learning lifecycle,
- no benchmark contract attached.

This is the most direct way to understand how the page works before moving to more specialized cases.

## What this workflow covers

This route is the right one when you want to:

- create a plan with a standard dataset,
- select one or more classical algorithms,
- attach one or more masking patterns,
- execute the plan in a single step,
- and move directly to result inspection.

In this workflow, execution is straightforward: one saved plan, one execution step, then results become available.

## What this workflow does not cover

This document does **not** cover:

- deep-learning configuration,
- train / validate / test phase control,
- PyPOTS-specific settings,
- shared benchmark contracts,
- shared mask banks,
- thesis-grade benchmark attachment rules.

Those belong to separate documents.

## The page at a glance

`Experiment_Runs` is organized around three main surfaces:

1. **Create Plan**
2. **Plan Manager**
3. **Select & Execute**

For the classical case, these three surfaces are enough to complete the full route.

```mermaid
flowchart LR
    A[Create Plan] --> B[Plan Manager]
    B --> C[Select & Execute]
    C --> D[Results Navigator]
```

## Before you start

A classical plan still needs a minimum set of registered assets:

- one dataset,
- one or more classical algorithms,
- at least one missing data pattern.

If these assets do not exist yet, prepare them first through the supporting setup pages.

## Step 1 — Create a classical plan

Go to **Create Plan**.

This is where the plan is defined and saved.
A plan is a reusable execution configuration. It describes what should run before any result is produced.

### Choose the execution class

Set **Execution Class** to **Classical**.

In this mode, the page stays simple:

- no DL split configuration,
- no window configuration,
- no training configuration,
- no masking protocol tabs,
- no reproducibility or artifact tabs specific to deep learning.

The classical route uses only the shared top-level form.

### Fill the base plan form

The classical form focuses on five practical inputs:

- **Plan name**
- **Dataset**
- **Metrics**
- **Algorithms**
- **Missing data patterns**

A good classical plan is usually easy to read from its name alone.
Use a name that helps you recognize the main intent later.

### Keep the benchmark contract out of scope

This document covers the case **without benchmark contracts**.
So for this workflow, do not attach a shared benchmark contract.

That keeps the plan in its simplest operating form.
The page may still display benchmark-related surfaces, but in this route they are intentionally left unused.

### Create the plan

When the form is submitted successfully, ImputeBench saves a run plan with a classical execution intent.

In this case:

- the requested execution class is `classical`,
- no DL-only configuration is attached,
- no missingness protocol is used as an execution authority,
- and the plan is ready for standard one-step execution.

## Step 2 — Review it in Plan Manager

After creation, move to **Plan Manager**.

This area helps you work with saved plans instead of treating them like one-off forms.
It is the right place to review what already exists and decide what to do next.

### What Plan Manager helps you do

For the classical route, the most useful actions are:

- review plan rows,
- filter by status,
- reopen one plan clearly,
- edit it,
- duplicate it,
- execute it,
- delete or purge it if needed.

This is especially useful once you have several variants of the same baseline experiment.

### What to look at in the table

The table is designed to keep the plan readable as an operational object.
The most useful columns for the classical case are usually:

- plan,
- dataset,
- algorithms,
- maskings,
- planned trials,
- requested execution class,
- actual execution class,
- status.

For a standard classical plan before execution, the requested execution class should read as `classical`, and the plan should still look like a saved configuration waiting to be run.

## Step 3 — Execute it in Select & Execute

Go to **Select & Execute** when you are ready to run the plan.

This is the surface where a saved plan turns into actual results.

### Select the plan

You can select a plan from the selection table and then choose it explicitly in the execution box.

The page also supports batch execution, but for a first classical workflow it is usually better to begin with a single plan.

### Execute the plan

Use **Execute plan**.

For classical runs, execution happens in **one step**.
There is no separate train / validate / test lifecycle here.
The system runs the plan and produces one result per algorithm × masking combination.

## Understanding the execution blocks

Once a classical plan is selected, the page shows several small operational blocks.
For this workflow, they should be read in a very simple way.

### Execution class & runtime truth

This block answers three practical questions:

- what was requested,
- what actually ran,
- and on which compute path.

For the classical workflow, the important expectation is straightforward:

- requested execution class: `classical`
- actual execution class: normally `classical`

The block also shows the compute engine. Even though this case is not a DL workflow, the runtime truth surface stays consistent across the page.

### Preflight summary

In the classical workflow without benchmark contracts, preflight is usually quiet.

There is no DL readiness logic to satisfy, and no strict benchmark contract to validate.
That means the preflight area should not be the main source of operator attention in this route.

### Benchmark truth

Because this document covers the case without benchmark contracts, the expected reading is simple:

- **Benchmark truth** should indicate that no benchmark contract is attached.

That is normal for this workflow.
It does not block standard classical execution.

## Understanding the classical lifecycle

For classical plans, the lifecycle is intentionally simple:

```mermaid
flowchart LR
    A[plan] --> B[execute] --> C[use]
```

The page renders that lifecycle explicitly.

### plan

The plan exists and is already saved.

### execute

This becomes completed once the classical execution succeeds.
At that point, the page can also show how many results were produced.

### use

Once execution succeeds, the outputs are available for downstream inspection and comparison.

This is the main difference from the DL route: there is no phase-based progression before results become usable.

## Step 4 — Continue to Results Navigator

After execution, the next natural step is **Results Navigator**.

`Experiment_Runs` already includes continuity actions for that handoff.
In the classical case, the important one is the button that opens the execution results in `Results_Navigator`.

This keeps the workflow smooth:

- create the plan,
- execute it,
- open the produced results,
- inspect the evidence in detail.

## A practical mental model

For the classical workflow, `Experiment_Runs` can be understood in one sentence:

> define a saved classical plan, execute it once, then move to result reading.

That is why this route is the best first reference for understanding the page.
It shows the core operational logic without the extra complexity of DL phases or shared benchmark governance.
